# PCL-Lite-service

PCL Lite 的**更新锚点**。这个仓库里只有两份清单，没有代码、没有 Release。

| 文件 | 谁在读 | 作用 |
| --- | --- | --- |
| `update.json` | 1.5.x 及更早 | 单指针，一行「去问哪个仓库」。**永远不能删** |
| `updatev2.json` | 1.6.0 及以后 | 多源清单，一次列多个仓库、每个带权重 |

新客户端先读 `updatev2.json`，读不到（404 / 写坏 / 超时）就静默退回 `update.json`。
所以**两份都要在**：老客户端只认前者，新客户端优先后者。

## 它解决什么问题

启动器必须写死一个地址才能知道「有没有新版本」。如果这个地址就是发布仓库本身，
那么仓库一改名、一换账号，所有已经装在别人电脑上的旧版本就**永久失联**了——
它们只会对着一个 404 报错，而且没有任何远程手段能把它掰回来。

所以把「地址」和「数据」拆开：

```
客户端（写死，永不改变）
    └──> 本仓库的 update.json / updatev2.json   ← 唯一锚点
             └──> 当前发布仓库/releases/latest   ← 随时可以改
                      └──> Release 自己提供版本号、资产、直链、SHA-256
```

## `update.json`

```json
{
  "update": "askbbtsk/pcl-lite/releases/latest"
}
```

`owner/repo` 之后的部分（`releases/latest`）只是给人看的，
程序取哪一版由那个仓库 Release 的 `prerelease` 标记决定。

**发新版不需要动这个文件。** 只有「发布仓库搬家」时才改那一行。

## `updatev2.json`

```json
{
  "schema": 2,
  "sources": [
    { "repo": "askbbtsk/pcl-lite", "tier": "official" },
    { "repo": "someone/pcl-lite-mirror", "tier": "mirror" }
  ]
}
```

### 权重

`tier` 可推导权重：`official` 100 / `mirror` 70 / `backup` 40 / `community` 25，
不写 `tier` 时按 `mirror` 算，也可以用 `weight` 直接写数字。

客户端**按权重分档，从最高档开始问**：最高档只要有一个源把版本报回来了就当场定下来，
**低权重档连请求都不发**。只有同一档内部（权重相等）才比版本号。

低权重不是「并列候选」，是「高权重全挂了才轮到」的替补。所以**不要**为了「让镜像抢先发版」
去调高它的权重——那等于让镜像决定所有人的更新。

### 身份校验

`tier: official` 的源免校验。**其余任何 tier 都必须在该仓库根目录放一份 `update.json`**
（能解析成合法指针即可），否则客户端会跳过它。

这是为了防止清单里混进别的项目：权重是发布者亲手写的，版本号是远端仓库说了算的，
只有「仓库里带着本项目的 `update.json`」这一条能证明它确实是本项目的镜像。

### 加镜像前先确认

1. 仓库**公开**（私有仓库对匿名用户就是 404）
2. 根目录有 `update.json`，内容是本项目的发布仓库指针
3. 它真的会同步本项目的新 Release，而不是一个早就停更的 fork

## 三条规矩

1. **仓库必须公开。** 私有仓库对匿名用户就是 404，和「不存在」无法区分，客户端只能报 404。
2. **仓库名和地址永不改变。** 改地址等于把所有旧版本一起掐断。真要换地方，
   要在新地址放一份内容相同的 json 并让旧地址重定向过去，而不是直接改客户端里的常量。
3. **不要归档、不要改默认分支名。** 客户端读的是 `main` 分支的 raw 地址。

## 背景

原来的锚点放在 `Pcl-Lite` 组织下。2026-10 那个组织被 GitHub 标记隐藏，
组织下所有仓库对匿名访问全部 404，清单的六条通道和 Releases 兜底源一起断，
客户端没有任何退路。这就是为什么锚点要放在一个稳定的个人账号下，
也是为什么 1.6.0 起要多源清单——单指针再怎么稳，也只有一个仓库在扛。

客户端侧的说明见主仓库的 `docs/UPDATE.md`。
